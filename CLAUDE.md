# Madrid in voxels

An interactive 3D map of central Madrid in 1 m voxels, running in the browser as a static site. It is a port of [warsaw-vibe-voxel](https://github.com/stared/warsaw-vibe-voxel) by Piotr Migdał (MIT).

## Project documents

- `PLAN.md`: phased work plan. **It is the source of truth for what to do and in what order.**
- `docs/research.md`: prior research (data sources, resolutions, comparisons).
- `NOTES.md`: technical notes you write as you learn how the pipeline works.
- `DECISIONS.md`: decision log (date, decision, reason, rejected alternatives).

## Language

**Everything in this repository is written in English:** documentation (`README.md`, `NOTES.md`, `DECISIONS.md`, `docs/`), code, identifiers, comments, docstrings, log and error messages, commit messages, and UI text.

- Spanish proper names stay as they are: places (Puerta del Sol, Paseo del Prado, Gran Vía), institutions and datasets (Catastro, Geoportal, Centro de Descargas del CNIG, PNOA).
- Field names from Spanish data sources (for example, columns of the tree inventory) are mapped to English identifiers when loaded; keep the mapping in one place and document it in `NOTES.md`.
- Map labels show the English name, plus the Spanish name where it differs, as Warsaw does with Polish and English names (from Wikidata).
- The user may talk to you in Spanish; answer them in their language, but keep everything written to the repository in English.

If the hook rejects a commit, rewrite the message without the attribution; never bypass the hook with `--no-verify`.

## Reference projects

This repository is **not a GitHub fork**: it starts from a snapshot of the Warsaw code, imported in a single commit with its own history, because every commit in the upstream history carries a Claude `Co-Authored-By` trailer. Both reference projects are cloned separately, **outside the repository**, as read-only references and sources of code: `../warsaw-vibe-voxel` and `../dtla-voxel`.

- Never add an upstream as a git remote to merge or pull from, and never bring upstream commits into this history. To adopt a later upstream change, copy the code and commit it as a new commit by the user, crediting the upstream commit hash in the message.

- **Original (project base):** https://github.com/stared/warsaw-vibe-voxel. Provides the full viewer (date, time of day, weather, seasons, pedestrians), the tile format, and the tree handling based on a municipal inventory with species.
- **Los Angeles (`../dtla-voxel`):** https://github.com/sigman78/dtla-voxel. Same tile format. Provides:
  - `prep_lidar.py`: point cloud to 0.5 m and 1 m rasters. Basis for processing the PNOA-LiDAR.
  - `fetch_*.py`: downloads that read only the area needed.
  - `voxelize.py`: 3D fill in 128-row bands so the full volume is never in memory. Needed for the full area.
  - `layers.py`: 2D fusion structure (ground, buildings, roofs, vegetation, bridge decks).
  - `road_markings.py` and street lamps placed every 36 m along kerbs.
  - `.github/workflows/` (GitHub Pages deployment) and the performance profiling harness (`artifacts/profiling`, `docs/rendering-profile.html`).
  - Optional: tree detection from NDVI and multiple returns, for trees missing from the municipal inventory.
  - **Do not use:** class inference (the PNOA cloud is already classified), palms, the Southern California palette, LA landmarks, Windows paths (`C:\data\...`).
- **Genoa:** https://github.com/zujk/genoa. A list of what is Warsaw-specific and needs changing.

## Working rules

1. **Follow `PLAN.md` phase by phase.** Mark each task as done (`[x]`) when finished. Do not start a phase until the user approves the previous checkpoint.
2. **At each checkpoint, stop and summarise:** what you did, screenshots produced, problems found, and what decision you need from the user.
3. **Data outside the repository.** All downloads go to a cache at `$MADRID_CACHE` (default `~/data/madrid-voxel-cache`). Never commit raw data. Only the generated tiles in `web/public/data` are versioned.
4. **Downloads limited to the area of interest (AOI)** and cached: if a file already exists, do not download it again.
5. **If a download cannot be automated** (web forms, captchas, services down), do not improvise alternative sources: stop and give the user exact instructions to download it manually and which folder to put it in.
6. **Coordinate system:** ETRS89 / UTM 30N (EPSG:25830). Check each source's CRS and height reference before combining them, and record the findings in `NOTES.md`.
7. **Do not change the tile format** (`tiles.py` and the viewer's reader) or the 1 m voxel size unless the plan says so. The resolution of the intermediate rasters, however, is a configuration parameter that depends on source density (1 m with NPC02).
8. **Visual verification:** use `scripts/screenshot.py` (created in Phase 0) to capture the viewer and save the images in `docs/img/`. Do not consider a visual task done without a screenshot.
9. **Small commits**, one per task, with English messages that say what and why, and no attribution of any kind (see "Authorship and attribution").
10. **Licences:** keep Piotr Migdał's original `LICENSE` (renamed to `LICENSE-warsaw-vibe-voxel`). When you copy or adapt code from `../dtla-voxel`, copy its `LICENSE` (MIT) as `LICENSE-dtla-voxel` and add a comment at the top of the copied file stating its origin. Keep data attributions in the README: OpenStreetMap (ODbL), IGN/CNIG (CC BY 4.0), Ayuntamiento de Madrid and Catastro under their terms.
11. **Log in `DECISIONS.md`** every non-trivial decision (chosen source, fusion rules, palette, area).
12. **Never modify `../warsaw-vibe-voxel` or `../dtla-voxel`:** they are read-only. Copy what you need into this repository and adapt it here.
13. **Voxel size as a constant:** in all new or adapted code for Madrid, use a single constant (`VOXEL_SIZE`, defined in one place and shared by pipeline and viewer) instead of hard-coding 1 m: object scales, distances, heights, conversions between metres and cells. Do not refactor the original Warsaw code just for this; simply avoid adding new hard-coded assumptions and keep the "1 m assumptions" section of `NOTES.md` up to date.

## Data sources

**Single source for elevation and classification: PNOA-LiDAR NPC02.** Heights are computed from the point cloud itself. Do not use digital surface models (DSM) except as described in Phase 2 of `PLAN.md`: mixing sources from different flights and dates complicates the pipeline and can create inconsistencies.

| Source | Use | Where |
| --- | --- | --- |
| PNOA-LiDAR 3rd coverage, NPC02 (CNIG) | Elevation (ground and surface), classification and NDVI. Cloud with basic editing, ~5 pts/m², flown March–May 2024. LAZ 1.4, 1 × 1 km tiles, RGB + near-infrared colour. Includes the bridge class (17) | Centro de Descargas del CNIG, LiDAR 3rd coverage series |
| OpenStreetMap | Streets, pavements, parks, water, rail, building types | Overpass API |
| Catastro INSPIRE | Building footprints and number of floors (municipality 28079) | Catastro ATOM service |
| Municipal tree inventory | Location and species of each tree | datos.madrid.es |
| Orthophoto (PNOA or Ayuntamiento) | Roof and vegetation colours | CNIG / Geoportal |
| Wikidata (CC0) | Landmark names (English and Spanish) and facts for info cards. Linked through the `wikidata=Q…` tag of OSM objects, never by name | Wikidata API (SPARQL or `wbgetentities`), fetched at build time |
| Ayuntamiento DSM 2023 (**optional**) | Only as a Phase 2 test if roofs come out with many holes. Photogrammetric raster (COG, 10 cm / 1 m), unclassified, from 2023 | geoportal.madrid.es, record on datos.gob.es |

Future (the pipeline must allow swapping the elevation or classification source without touching the rest):

- **Municipal 2026 flight** (LiDAR 30 pts/m², 7 cm imagery), awaiting publication on the Geoportal.
- **PNOA-LiDAR NPC03** for Madrid (improved basic editing): same files with better classification. Not yet published.

## Commands

```
# Python dependencies (pipeline + screenshot harness)
uv sync

# Madrid data: downloads (cached) -> rasters -> fusion -> web/public/data (~25 s for the test area from the cache)
sh scripts/build_data.sh
# the PNOA-LiDAR LAZ tiles are downloaded by hand; this lists the ones the AOI needs and checks them
PYTHONPATH=scripts uv run python scripts/fetch_pnoa_lidar.py

# Viewer in development (web/ pins pnpm; the lockfile is pnpm-lock.yaml)
cd web && npx -y pnpm@12.11.2 install --frozen-lockfile && npx -y pnpm@12.11.2 exec vite

# Screenshots (starts the dev server if needed; writes docs/img/<name>.png)
uv run python scripts/screenshot.py <name> --view overview --date 6-15 --hour 17
```
